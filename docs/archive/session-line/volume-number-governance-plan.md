## 0. 裁定（决定放前面）

| # | 裁定 | 理由（一句话） |
|---|---|---|
| D1 | 身份仍是**数字卷号**，不做 UUID | 号已当主键用在四处（文件名 / 血缘 `parent`+`atSeq` / 每卷账本 / 检索手柄）；换 UUID = 二三十个文件穿透 + 丢掉「案卷 12」这个可念手柄 |
| D2 | **号一经发出，永不复用**（发号账落盘） | 复用是整个「死卷冒充新卷」bug 族的根（真机事故见 §1）；拔根 ⇒ 那一族从「有」变「结构上不可能」 |
| D3 | 发号账**独立成文件**，不寄生 `_index.json` | `_index` 是**可丢弃投影**（版本不认即整份重建、惰性载入、防抖 fire-and-forget 写）——单调事实不得住在会被重建的缓存里（单一权威源） |
| D4 | **有名卷**的常显号收成两处：书脊档号 + 卷首眉行 | 其余位置都是「名字旁边再报一次号」的重复；书脊的号是「题名两栏截断后唯一可靠的身份」（守护测试原文），卷首恰一次是 2026-09-16 用户拍板 |
| D5 | A 只改**呈现面**，不动数据结构；**无名卷的号即其名**（兜底显示全留） | 退掉的是**重复显示**，不是身份——号继续存在、继续可按号检索、继续进诊断文案；无名卷没有名字，号是它唯一标识 |

**命名说明**：本篇沿用「卷号」（机读注记与代码里的 `id`／`sessionNum`）；它在 UI 上的读法是「档号」，
但那是**呈现层的说法**，不是新的实体。术语不新增。

## 1. 现状与病根（证据）

**发号器**：`src-ui/src/state/session-store.ts` 的 `nextSessionId`（纯内存，初值 1）。

| 面 | 位置 | 语义 |
|---|---|---|
| 起卷占号 | `ui/chat-session.ts:594` | 任何 `await` 之前占号（并发双回车不铸同号；占号不回退，epoch 丢弃也烧号） |
| 立枝取号 | `app/chat/session-branch.ts:452-455` | `max(内存号, 磁盘最大号+1)`——「宁可多发一号也不赌」（撞号 = 原子替换写覆写既有卷） |
| 重启对账 | `ui/chat-session.ts:1471` | `max(内存号, 磁盘最大号+1)` ⇒ **重启回退**：删掉高位卷后，那些号会被重新发出 |
| 摊开抬下限 | `ui/chat-session.ts:1741` / `:1878` | 续开/批恢复大号卷后抬内存下限（不落盘） |

**复用为什么是真病灶**（不是洁癖）：`docs/archive/session-line/session-tree-plan.md` §12 记了真机事故——上一代死卷残留的
`{id}.json` 正好接住今天新发的同号卷，三个子卷**顶着 9/6 死卷的名字**且不会自愈。为此今天长着三台机器：
读面「同代校验」（`ui/chat-session.ts:1480` 起）、已删卷写拒绝名单（`_removedVolumes`）、立枝的「宁可多发一号」。
**这三台机器的存在理由，全是「身份是可复用的小整数」。**

**先例**：退役的总目 `_ledger.json` 里本来就有这一栏（`docs/archive/session-ledger-plan.md:56-76`：
`"nextSessionId": 231` +「发号 = max(总目.nextSessionId, scanMaxSessionId(dir)+1)」）。总目因**摊开集**用途退役
（`ui/chat-session.ts:1258`），**发号这一半本批补回**——形状照抄，用途收窄到发号。

**本批顺带修的雷**（审计新发现）：`session-branch.ts:452` 在 `await scanMaxSessionId()` **之前**取了 sess
快照，`:454` 读的是陈旧值 ⇒ **并发两次立枝可铸同号并互相覆写**（`write_log` 是原子替换写）。`createNewSession`
2026-09-09 已修过同族问题，立枝漏了、且零测试覆盖。本批取号重排后**同步占号**，雷随之拆除（回归用例见 §4）。

## 3. B：发号账（`_issue.json`）

**owner**：`src-ui/src/ui/chat-session.ts`——卷号生命周期的唯一 owner（发号点与对账点都在此，且
`_volumeCatalogs`/`_removedVolumes`/每卷写链三个同族模块态也在同文件）。不新建模块：新模块只会多一条
import 边（`ui/chat-session` ↔ `composition` 成环事故见 `:1770` 注），收益为零。

**文件**：`{工作区}/.lantai/sessions/_issue.json`，形状 `{"ver":1,"next":22}`。走下划线保留名 + 既有 seam
（`read_volume` / `save_volume`，与 `_index.json` 同款）——**零 Rust 变更、零 RPC 契约变更、零格式版本升级**；
卷集判定只认 `.ndjson` 且跳过 `_` 开头，故账文件对既有清点面天然隐形。

**语义**：`next` = 下一个可发的号 = 已发出的最大号 + 1，**单调只增**。

```
读（每 root 每进程一次；坏档/缺席 ⇒ 当 0 + warn 可见）
对账 装配 / 立枝：next = max(内存下限, 磁盘最大号 + 1, 账 next)   ← 这两处本来就要扫盘
     起卷（发号路径）：next = max(内存下限, 账 next)              ← 不扫盘（见取舍 2）
发号 ensure（await 读账）→ 同步占号（claim→setState 之间零 await）→ 写账（await）
```

**五条关键取舍**：

1. **写账要 await（不是 fire-and-forget）**：否则「发出号 → 立刻崩溃 → 该卷被删」仍能复用——账的全部意义
   就是关掉这个窗口。写账发生在**卷物化之前**（先记账再建卷 ⇒ 崩溃只烧号、绝不回收）。写失败**可见**
   （warn + toast 一次），不静默、不阻断建卷。
2. **对账取 max，账不参与回退**：`scanMax + 1` 这一项**长期保留**（手工拷入的卷 / 账丢失 / 旧盘），
   但**只在对账时本来就要扫盘的两个入口参与**（装配 / 立枝）。**发号路径不扫盘**——起卷今天只认内存
   （「发号同步占位」纪律），盘上号由装配对账与开卷抬下限覆盖；把目录枚举塞进发号会改变既有语义
   （2026-09-21 全量回归实测：9 例因它变红，收窄后零漂移）。账那一项则每次都在场，且账读取每 root
   每进程一次 ⇒ 第二次起发号零 I/O。
3. **版本不认的账，定向拒读、绝不覆写**（同卷日志格式纪律）：盘上是更新版兰台写的账 ⇒ 本 build 只 warn
   + 退回磁盘对账，**不写它**——覆写会抹掉新版已发出的号段，降级运行反而制造复用。
4. **内存键归一**（`D:\ws` 与 `D:/ws` 是同一份盘上账；`workspaceSessionsDir` 只剥尾分隔符、不转反斜杠）
   ⇒ 两条键各持一份水位是错的。
5. **旧工作区不迁移**：无账 = `next` 记 0，首次发号时补写账；历史已删卷的空号**不追溯**（与今日
   `scanMax+1` 的起点一致）。

**INVARIANTS 对齐**：#1——模块态 `_issueLedgers: Map<root, …>` 键控自清理（与 `_volumeCatalogs` 同族，
声明处注明归属）；#12——写账是逃逸所有权的在途写 ⇒ 沿用 `getWorkspaceEpoch()` / `isCurrentEpoch()` 代际校验
（对账入口内建）。另：`setNextSessionId` 访问器改为**只增**（旧语义可拉低水位 = 直接拆 D2 的承重面）。

**不做（本批范围外，另立）**：不拆 `_removedVolumes` 与同代校验（账让它们从「必需」降为「冗余保险」，
拆要另一份证据）；不收口「卷集判据三份手抄」（`chat-session.ts` 两处 + `chat-core.ts`）；不动 Rust 侧
`scan_sessions_dir` 的 `.json` 计数口径（与 TS 卷集不是同一把尺子，属既有发散）。

## 4. 测试计划

## 6. 风险与残余（诚实栏）

| 风险 | 现状 |
|---|---|
| 账写失败（磁盘满/被杀） | 可见 warn + toast；该窗口内号仍可能复用——账不承诺防「账本身写不进去」 |
| **工作区移除 / 手工删会话根**（`workspace.rs:247-255` `remove_dir_all`） | 账与卷**同生共死**（语义自洽：卷都没了，号无从复用）；但删根后重开同一路径 ⇒ 从 1 重发。**这是账关不掉的残余** |
| **多窗口/多实例**（未发现单实例守卫；`write_atomic` 无 CAS） | 两实例都读 `next=20` 都写 21 ⇒ 都发 20。今日同样撞号（两份内存发号器），**账不使情况更坏也不修好**；进程内「两 panel 同 root」的读-改-写交错由「同步占号 + 每 root 一本内存账」防住（生产暂单 `ChatCore`） |
| 工作区被拷到另一台机器 | 账随工作区走，号段一致；同时开两台 = 上一行同险 |
| 版本升级 / 手工删账 | 定向拒读或退回 `scanMax+1` 并 warn——比今日不劣，不炸 |
| 同代校验/已删卷名单变成冗余 | 本批**不拆**；账稳定跑一段后另立「拆冗余保险」评估（需要证据：账在场时那些路径是否真的永不触发） |

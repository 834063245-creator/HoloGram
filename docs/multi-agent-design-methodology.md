# 多 Agent 集群设计方法论

> 一份可**跨领域复用**的设计手册。教你怎么把一支多 Agent 集群从"几个会说话的模型"
> 组织成一个**有分工、有边界、有人负责、能接手大型真实工作**的团队。
> 本文**不绑定任何行业**——它讲的是"该想清楚什么、按什么顺序想"这类通用的心智模型与决策，
> 适用于任何有"明确产出单元 + 多人/多进程协作"的复杂领域。
> 软件工程只是这套方法**已经验证落地的一个实例**，放在附录供对照，不是正文的主线。

## 1. 为什么需要这套方法

单个模型 / 单个 Agent 在大型领域（一个庞大的代码库、一整套法规文献、一条复杂的供应链）
里，普遍存在一种症状：**"局部正确，整体崩盘。"**

- 单个 Agent 应付一个小范围时顺手；一旦工作跨到了多个子领域、规模一大，
  它就开始"这里改对了、别处连带坏了"。

它不是因为模型笨，而是因为**认知缺陷**（见第 3 节）。为了对抗这种缺陷，最自然的反应
是**分工**——把一个大领域切成若干小单元，每个 Agent 只负责一小块，让每个说清楚一件事。

但分工本身会带来一串新问题：

- 每个 Agent 的**局部视野**变小了（它看不到全局约束）。
- Agent 之间的**信息会割裂**（谁改了会影响谁，彼此不知道）。
- **协调的负担**被抛给了那个唯一有全局视野的点——通常是发起这一切的人。
- 规模一大，人（或任何单一中枢）的带宽撑不住，于是整个集群开始失序。

**这套方法的目的是：在"分工带来的专注"和"分工带来的割裂"之间，
找出一套可复制的设计流程，把集群组织成有序系统，而不是把复杂度全部转嫁给人类。**

**适用前提**：你有意让多个 Agent 协作，并且这项工作能被切分成**相对独立的产出单元**。
如果任务小到一个 Agent 能独立完成，就不需要这套方法——先别过度工程。

## 2. 核心心智模型：从"多 Agent"到"岗位"

最容易进入的误区，是把多 Agent 系统想象成"一大群平级的、会互相聊天的模型"。
**别这么想。** 那会立刻引向"网状通讯"、"每个都该有全局视野"之类的病态设计。

正确的内心模型是**一个组织 / 一家机构**：

- 组织里每个人都有**明确的职责、边界、上级、可调用的资源**。
- 组织不是靠"大家互相发消息"运转的，而是靠**分工 + 上下级 + 规矩/契约**。
- 每个人的记忆和上下文是**他自己的地盘**，不是共享的。

把这个映射到 Agent 世界，核心概念就一个字：**岗位（role）**。

> **一个岗位 = 一个 Agent 的完整封装**：它叫什么、能碰什么、不能碰什么、
> 卡住找谁、把活派给谁、靠什么指导行事。
>
> **多 Agent 系统的设计单位，不是一个会话、不是一个模型，而是一个"岗位"。**

一旦你以"岗位"为单位思考，原本混乱的问题全部变成可管理的清单：

- "我要哪些岗位？" → 来自工作领域的自然切分。
- "这个岗位的边界在哪？" → 来自领域中单元之间的关系结构。
- "这个岗位卡住了找谁？" → 来自那个单元相邻的职责。
- "这个岗位怎么干活？" → 来自它能调用的工具与委派能力。

整份方法论，就是回答这些清单题的流程。

## 3. Agent 的认知现实（一切的出发点）

在动手设计之前，必须诚实地接受 Agent（LLM）的三个认知事实。
**这套方法的所有决策，都从这里出发。**

1. **不会累，但会被稀释。**
   模型不会"累"、不会因疲劳停机；但上下文越长，噪音越多、注意力越被稀释，
   输出质量实打实地下降——这正是"委派以保持上下文整洁"（第 13 节）的立论根基。
   而它在大型领域里**缺两样东西**：全局视野，和自我反思 / 自愈能力。
   它手握工具、文档、技能，仍然会"局部正确、整体崩盘"——病根在这里。

2. **局部视野是分工的代价。**
   把任务切细，能让每个 Agent 的上下文更干净、更专注。
   但切得越细，每个 Agent 对"全局约束"越看不见。
   **不要天真地以为"切得越细越好"——细到拐点之后，增益被盲区成本吃掉。**

3. **它不会自己察觉"我越界了"或"我的改动影响别人"。**
   权限限制能让它"动不了"，但**"动不了"不等于"它会正确处理"**。
   一个被权限挡住、又没有出路指引的 Agent，会乱搞、会停工、会做出预期外破坏。

**推论（直接塑造本方法）：**

- 它缺"全局框架" → 我们通过注入一份全局约束（见第 4 节）补。
- 它缺"自愈" → 我们通过"人 + 负责人 Agent"的层级责任（见第 14 节）补。
- 它"动不了 / 越界时该找谁" → 我们通过**可寻址的点对点航线路由**（见第 8、9 节）给出路。
- 它"该专注什么" → 我们通过岗位边界 + 上下文纪律（见第 6、11 节）保证。
- 它"该看多少 / 能动多少" → 我们通过**粗粒度分域 + 读放开写收紧**（见第 12 节）保证。

## 4. 第一性决策：全局视野怎么给

**结论先行：全局性信息，用一句自动注入的权威文档统一携带，而不是做一个需要多方维护的动态"白板"。**

### 为什么是注入，不是共享白板

"全局视野"里的大部分内容，属于**先验可知的静态约束**：

- 整个领域的顶层原则、工作宪法
- 不可触碰的红线 / 纪律
- 高层的单元地图与依赖方向
- 跨单元的共同口径 / 契约 / 术语

这类信息有一个共同点：**低频变更、权威唯一、所有 Agent 开工前就该一次性读齐。**
把它们做成一个动态的、需要多方共同维护的"共享状态"，是**过度设计**——
它引入了同步问题、一致性问题、谁改谁负责问题，而所有这些本不需要存在。

正确做法：**一份全局权威文档（在软件工程里常叫 `AGENTS.md` 之类），
在每次会话 / 每个 Agent 启动时自动注入。**

- 它定义"全局是什么样"。
- 它一次满足所有岗位的"全局框架"需求——**不占通讯带宽，无同步难题。**

### 边界：注入只管"起点"，不管"过程"

注入解决的是**开工前的对齐**。它解决不了两类事：

1. **动态中间态**：谁改了 X、谁因此受影响、谁在等谁——这些发生在分工之后，
   是运行时才产生的状态，没法预先写进一份静态文档。
2. **动态全局规则**：需要随着工作演进不断调节的、由负责人拍板的规则。

这两类怎么处理：**动态中间态**由程序层任务传导链承接（见第 10 节），
**动态全局规则**由责任层承接（见第 14 节）。这里只钉死一条：
**别把动态的东西硬塞进静态注入文档里，也别为动态状态造一个要大家维护的白板。**

## 5. 第一性决策：协同靠什么

**结论先行：协同优先靠"共享的权威上下文（注入 + 人维护的真相源）"，
而不是靠"Agent 之间消息直连"。**

两道决策顺序很重要：

1. **凡是能靠上下文对齐的，就别靠消息。**
   静态约束、共同口径、规则——全走注入（第 4 节）。一个 Agent 该知道的，
   在它开工前就该已经在它上下文里，而不是等同事"传达"。这最小化了消息网络的必要性。

2. **真正需要"联系"的，只有"我的动作影响到了边界外的某个产物 / 单元"。**
   这种事件类型很窄，值得用一种**可寻址的点对点**方式处理（第 8、9 节）——
   对那个目标物倒查其负责人、单点联系，而不是建设一个无差别广播的"网状消息总线"。

**为什么反对"网状平级通讯"：**

- 网状通讯要求每个 Agent 知道"谁是管这个的"——这本身就是巨大的全局知识。
- 全网广播制造噪音，每个 Agent 的上下文被与它无关的信息污染。
- 真正的多 Agent 崩溃，绝大多数不是"消息不够"，而是**"职责不清 + 全局约束没对齐"**。
  前者要用层级和边界治，后者要用注入治，都不是加消息。

**所以协同的优先级是：**

```
1. 注入对齐（静态的、开工前该知道的）   —— 成本最低，先用
2. 权威真相源（人维护的、演进中的全局规则）—— 人在环上，居间
3. 可寻址点对点通讯（对目标物倒查负责人，触发式的）—— 只在真正越界时才用
4. 网状平级通讯（无差别广播）             —— 尽量避免 / 最后手段
```

另有一类共享状态——任务状态（谁在干什么、到哪了、产物在哪）——不属于通讯，
属于程序层任务传导链（见第 10 节）：harness 单写者维护、Agent 按事件读写，
不占任何 Agent 的通讯带宽。

把协同从"消息"改成"上下文 + 可寻址的触发式联系"，是让集群规模可扩展、
让人的心智负担可承受的关键。

## 6. 设计单元：一个"岗位"的完整封装

**这是整个方法论的核心章节。** 每个岗位，都要针对它的角色做**一整套完整的设计**，
而不是"给它一段人设提示词"。

一个完整岗位至少包含七个方面。设计任何岗位时，逐一回答这七个问题：

### 6.1 上下文（context）—— 它带着什么思考

- 它开场带什么？(全局索引、所属单元、职责声明)
- 它长期需要什么但不想每轮重复？(记忆 / 长期状态)
- 它该"手动查"什么，不该"常驻"什么？(常驻的是低频权威信息，高频可变数据该按需查)

### 6.2 技能（skills）—— 它用什么方法论干活

- 它的专属技能包是什么？(领域流程、执行准则)
- 哪些技能是"必需"(放进来)，哪些是"可查"(不该占常驻上下文)?

### 6.3 权限—— 它能读写什么

- 它被允许动哪些单元 / 资源？(明确列出来)
- 它**不被允许**动什么？(同样明确列出来——边界要双向清晰)

### 6.4 沙盒 / 行为范围—— 它的实际动作边界在哪

- 它实际执行命令、写文件、调网络的作用半径？
- 这个半径如何约束"它能造成的破坏范围"？

### 6.5 能力集合—— 它能动用哪些工具

- 它需要哪些能力来干活？(工具集)
- 哪些工具是有意不给它的？(权限的第二层)

### 6.6 通讯契约—— 它越界了找谁（可寻址，不是硬写死）

- 它的**工作域**是什么？（这个岗位持有哪些目标物 / 归属哪些单元——见 7）
- 遇到**边界外的目标**，它如何**找到**该目标的负责人？（倒查寻址，见 9）
- 它如何**拿到**那位负责人的通讯地址？（查询程序层注册表，见 9）
- 它该走哪条路（通知哪个 channel）？（见 8）

**关键转变**：路由**不是**"每个岗位硬写死 A 只能找 B"。而是每个岗位领取了固定的**工作域**之后，
遇到边界外目标物时，**从目标物倒查负责人并单点联系**。这更像真实组织——
你不是"预设了和谁是邻居"，而是"这个东西归谁管，我查一下，然后找他"。寻址的权威来源见第 9 节。

### 6.7 委派—— 它把活派给谁

- 它能不能 spawn 下层子 Agent 来实际干活？(见 13)
- 如果可以，它作为"父"，承担什么协调责任？

> **设计一条检验标准：** 如果这个岗位被权限挡住、或遇到边界外的事，
> 它的**下一步行动是这个岗位设计里白纸黑字写好的**——
> 不是"它临场发挥"，而是"它的设计给了它出路"。做不到这一条的岗位设计是残缺的。

## 7. 岗位边界怎么切：看结构，不靠直觉

这是整套方法里**技术含量最高、也最容易被低估**的一步。

**岗位边界不应由设计者的"感觉"来切，而应由领域中单元之间的"关系结构"来决定。**

### 为什么不能靠感觉

- 你按直觉切出的"单元边界"，可能和真实的关系结构错位。
- 边界切错 → 一个岗位要动的东西横跨多个"单元" → 权限频繁越界 →
  通讯频繁触发 → 集群在边界处不断震荡 → 比人类团队更乱。

### 正确姿势：让"产出依赖"告诉你边界

几乎所有领域的单元，都存在一种可观察的**依赖关系**：
这个单元的产出，会决定 / 影响另一个单元的输入。

- **代码工程**：一个模块引用另一个模块的接口 → 调用依赖。
- **法规 / 文献**：一份规章引用另一份条款；一篇论文引用另一篇的结论 → 引用依赖。
- **供应链**：一种物料是另一种的前置 → 物料依赖。
- **科研管线**：一阶段的结果作为下一阶段的输入 → 阶段依赖。

**"依赖"的本质是通用的：某个产出的改动，会波及依赖它的别处。** 边界就切在低依赖处。

1. **画依赖关系**：谁产出 → 谁消费。把强耦合、会被单个变更波及的集群圈成"一个单元"。
2. **找破坏面**：哪些产物被多方依赖？改动它会影响谁？→ 这些都是"交界岗位"，
   它们的通讯和边界必须设计得最严格。
3. **定边界**：单元之间应该**低耦合、高内聚**。边界画在低依赖的切线处。

**没有依赖图怎么办**：依赖图是最优选，但很多领域没有现成的"图"可画。
那时就退而求其次：**由领域专家手工梳理"哪些改动会连锁影响别处"，再切边界。**
依赖的可视化结构越清楚，边界越可靠。

**一句话**：**"这个单元该归谁、动它最安全"，由领域中的关系结构决定，不由岗位表决定。**
如果手头连依赖梳理都没有，至少做一轮"哪一处改了会连带影响别处"的辨识，
再切边界——**永远先看结构，再定岗位。**

> 推论：**岗位边界是否合理，是可以被检验的**——如果一个"负责人岗位"的职责
> 在频繁跨边界，多半是切分单元错了，而不是通讯写得不够多。

## 8. 分层拓扑与通讯纪律

### 分层拓扑：粗粒度分域 + 层级兜底

分工应**粗粒度**，而非无限细分。理论上可以像一家大公司"部门 → 小组 → 具体负责人 → 执行者"
那样细分到最小粒度，但在 Agent 协作里，这种细度**难以实施、复杂度过高**（见第 17 节的诚实声明）。

推荐的简化拓扑：

```
用户（项目/工作负责人，维护全局真相源 + 最终拍板）
  └─ 大工作域（按前端/后端这种粗粒度切，或按子领域切）
      └─ 域负责人（统筹整个域，兜底）
          ├─ 域内按需分配单元负责人
          │    单元负责人域内放开权限、放开手脚
          └─ 越界 / 兜不住 → 沿层级向上找上级负责人
```

- **域负责人**：统筹整个域，负责派活、盯进度、接住下属任何越界；是**兜底**的主要承担者。
- **单元负责人**：域内细分负责人，在所属域内**放开手脚**，遇到问题交由上级兜底。
- **用户**：只管全局真相源 + 关键决策，不逐条盯执行。
- **兜底有边界**：上级负责人能兜底，但也可能兜不住——"兜底"不是无限能力，
  只是给了越界一个出口（见第 14 节责任层）。

**为什么粗粒度更好**：
- 大区域负责人兜底可以防止**统筹黑洞**——每个越界都有一个明确的上级可以接。
- 域内负责人在域内放开权限，避免"过度细分"导致的大量跨域震荡。
- "域内放开、跨域收紧"比"一律锁死"健康。但**放开的是域内的自由度，不是域边界的模糊**——
  边界要粗而清晰（见 7），不能粗而含混。

### 通讯纪律：可寻址的点对点，非网状

"点对点"的正确含义**不是**"硬写死 A 只能找 B"。它是：

> 每个岗位领取固定**工作域**后，遇到边界外个目标时，通过**通讯录倒查**该目标的负责人，
> 拿到地址后**单点联系**。不是广播，也不是预设邻居。

纪律四条：

1. **可寻址，不网状。** 越界时对目标物**倒查负责人并单点联系**（见 9），而不是广播所有人。
2. **触发式，不持续。** 只在真正发生"我的动作涉及边界外目标"时，才联系。
3. **通讯 ≠ 信息获取。** 读权限全放开（见 12），Agent 应自己读工作库拿信息；
   **通讯只在"要改动边界外的东西 / 需要协调"时才触发**。这大幅降低通讯频率。
4. **能靠上下文 / 直接读取解决的，不走进通讯。** 这永远是第一优先级（见第 5、11 节）。

> 为什么用**可寻址的点对点 + 分层**而非**网状平级**：
> 网状要求每个 Agent 掌握"全局组织图"且时刻同步。分层 + 倒查把"组织图"交给一个
> **程序层注册表**（见 9）按需查询——每个岗位只按需拿到它要联系的那一位负责人，
> 不常驻全表。**主动寻址而不预知全局，可扩展性来自"按需地址"而不来自"全表记忆"。**

> **读全放开，通讯不为信息**：Agent 获取任何所需信息都不该靠"一直打电话"。
> 就像公司里你能看到整个工作库、能拿所有信息，但**不该你动的东西就不要动**。
> 边界的目的从来不是**阻碍获取信息**，而是**约束改动**。限制信息获取，就是一种
> "只把门关上门但不出路"的设计——这也是第 15 节反模式 B 的一部分。

## 9. 通讯录：程序层注册表与倒查寻址

"越界找谁"的寻址，需要一个**可靠、不靠人记、不靠 Agent 猜**的权威来源。

### 通讯录 = 程序层注册表，不是白板

通讯录是**程序层统一维护的注册表**的物化视图。每当系统**注册**一个新的工作域 +
指派负责人，或**注销**一个 Agent，注册表自动更新——寻址数据随之变化，
**不需要任何 Agent 或人来手动登记、同步**。

- **单一写入**：由程序层 / harness 的生命周期流程统一管理（注册 → 注销）。
- **只读查询**：Agent 只能查询，不能改。
- **不是"共享白板"**：白板的病根是"多方共同写 + 人力维护"；这边是**程序单点权威写、Agent 只读查**，
  不引入同步与一致性问题，也**不成为新的心智负担**。

> 记忆锚点：**注册 → 注销流程 = 通讯录的增删。** 域切出并指派负责人，就注册一条；
> Agent 注销，就移除一条。通讯录永远跟运行时的"当前有谁"保持一致。

### 倒查寻址：从目标物到负责人

寻址不是"预设邻居"，而是**倒查**：

```
遇到边界外的 目标物（某个文件 / 目录 / 段落 / 配方 / 条目 ……）
   ↓ 查程序层注册表
解析出该目标物所属的 工作域
   ↓
得到该域的 负责人通讯地址
   ↓
单点联系那位负责人
```

- 每个被切分的单元（工作域）在注册表里**登记了归属负责人**。
- 倒查 = 查注册表，而不是硬遍历一堆元数据。
- 粒度**粗**：按前端 / 后端这种大域查询，或按子领域查询，复杂度和成本都低，够用。

### 寻址依赖第 7 节的边界定义

通讯录能"倒查"的前提，是第 7 节已经用领域结构把**单元与负责人**对应清楚了。
通讯录本质是**岗位边界表 + 负责人指派的可查询索引**。若边界切得含糊，通讯录也会含糊——
**先有明确的域和归属，才有可靠的倒查。**

### 读放开，沟通才少

正因为**读权限全放开**（见 12），Agent 绝大多数情况自己读工作库拿信息，
只在**要改动边界外目标 / 需要协调**时才触发通讯。通讯频率被压到最低，
注册表的查询量也随之可控。

## 10. 任务传导链：动态状态的家

第 4 节钉死了"动态中间态不能塞进静态注入文档"。这一节回答：**它到底住哪。**
答案是程序层维护的一条**任务传导链**——它不是消息机制，也不是共享白板，
而是任务状态的**单写者权威记录**：由 harness 程序层统一写、Agent 经规定事件间接读写。

### 10.1 共享可变状态只有一个：任务状态

"共享可变状态"这个词常被想复杂。拆开只有两种，命运完全不同：

| 状态 | 内容 | 谁写 | 生命周期 | 默认是否共享 |
|---|---|---|---|---|
| **任务状态** | 任务的目标、输入、当前阶段、owner、产物位置、在等谁 | 程序层单写者（Agent 经规定事件间接写） | 跟随任务，完成后归档 | **必须共享** |
| **Agent 工作状态** | 读过什么、试过什么、卡在哪——它的思考过程 | Agent 自己 | 跟随 Agent 会话 | **默认不共享** |

**任务与 Agent 生命周期解耦**：任务比 Agent 活得长。Agent 可以死、可以换、可以重启，
任务状态在 harness 手里不丢。Agent 不需要"记得自己在哪"——位置信息根本不在它脑子里，
在传导链上。把任务状态寄居在某个 Agent 的上下文里（反模式 G），是这个架构最经典的死法。

### 10.2 链是记录，不是计划

传导链**不是开工前规划出来的 DAG**。任务进来时是个模糊意图，指望 LLM 一次性切成
精确任务图，是长程规划——那是它最弱的能力，失败是大概率事件。

链从**委派事件**里长出来：负责人说"spawn 一个去复现这个 bug"——这句话就是一个事件，
harness 记下，链上多一个节点。每个节点只要求委派那一刻的信息是对的：目标、输入、依赖谁。
这是单步决策，模型现在就能可靠地做。整条链看着复杂，其实是几百个单步决策沉淀出来的。

因此链的精确度分布是**过去精确、未来模糊**，同一结构里共存三种密度：

- **意图区**（向前）：还没派下去的事。粗、少、随手改——负责人脑中的待办清单。
- **活跃区**（当下）：正在干的节点。每个有 owner、状态、产物。精确。
- **历史区**（向后）：干完的。完整、可回放。

### 10.3 传导纪律：正常向下，异常向上，默认零通讯

传导链的运行纪律只有三条：

1. **正常流只向下**：委派、交付，走链不广播。
2. **异常流只向上**：失败、越界、卡死，沿链向上回传。
3. **默认零通讯**：没有事件发生，就没有消息。

任务之间的关系是 DAG：每个子任务各自拥有一条传导链，父任务在汇聚点等所有子链回传。
于是第 8 节"触发式通讯"在这里有了精确落点——**通讯只在链上的事件点发生**，
事件就是"我的动作影响了边界外的目标"。

一条必须由 harness 强制执行的不变量：**每一次 spawn，必须有且仅有一次回传
（done / fail / timeout）。** harness 不负责安排链，只负责盯着这条不变量。
链的运转靠的是这条规矩的笨而执着，不是 Agent 的聪明自觉。

### 10.4 移交：传指针，不传记忆

负责人"接住"失败的子岗位（第 13 节），最贵的问题是：前任脑中的局部信息怎么传给接手者。

答案是**不传记忆**：传**状态指针**（任务到哪了、产物在哪、卡在哪个节点），
让接手者**读库重建**。前任的思考过程压缩成几句摘要跟着传，能传多少算多少，
传不了的靠读放开补——这与第 12 节"读全放开"完全自洽：上下文移交的最佳实现，
就是把交接成本转嫁给读取能力。

### 10.5 门控是完成定义的一部分

传导链上最阴险的破坏不是越界，而是**合法改动的波及**：A 在自己域内合法改了东西，
B 域依赖这个改动，悄悄碎了。A 没有任何越界，A 也不可能知道——因为"谁依赖我"
是全局知识，而这个架构的整个设计都在避免全局知识。

所以发现波及不靠自觉，靠**门控**：测试、构建、校验。门控不是道德要求，
是任务状态机的必经节点——**状态流转到"完成"的定义里包含"门控通过"**，
不过门控，任务不算完，harness 强制。

门控发现失败后的链是结构化的：**负责人自查 → 确认是边界外改动 → 倒查寻址 →
单点联系对应负责人（第 9 节）。** 每一步都不需要全局智慧或长程自主——
这是把"需要全局智慧的预知"换成"结构化的检测-通知链"，当前模型能力够得着。

### 10.6 节点监控：可监控的是行为，不是内心

把每个 Agent 当节点，它对外做的每件事（spawn、读、写、门控、回传）都是可记录的事件，
串起来就是**轨迹**。程序层随手可查：谁在跑、卡了多久、它干过什么、它的下线都干了什么。

- **可监控的是行为轨迹，不是推理过程。** 上下文里的盘算看不到，也不需要看——
  记的是手，不是心。这正是"工作状态默认不共享"能成立的原因：审计靠行为，不靠窥视。
- **轨迹证明"动没动"，门控证明"对不对"。** 轨迹是审计工具，门控是验收工具，别混。
- **事件粒度是设计题，不是越细越好。** 记到"改了哪个域、交付了什么、状态怎么流转"
  就够；每次工具调用的细账按需查，别常驻图上，否则是数据沼泽。

节点轨迹 + 传导链 + 倒查寻址合起来，整个集群变成一张**可查询、可回放、可审计的活图**。

### 10.7 四个真实杀手

链会漂移。四个杀手全有名字，也全有笨而有效的对策：

1. **谎报完成**：Agent 说 done，活没干完。→ 门控是唯一真相（10.5）。
2. **链错了没人能改**：以为 X 依赖 Y，其实不依赖；漏了 Z。→ 链必须可变，
   改链是日常操作不是异常——意图区本来就是负责人随手改的。
3. **孤儿任务**：Agent 死了，节点永远 in-progress。→ 活跃节点必有 owner，
   owner 必有心跳；心跳停、超时未回传 → harness 回收并回传 fail。
4. **harness 变瓶颈**：什么都从它过。→ harness 不在消息路径上，
   只做两件事：记事件、答查询。活干在产物里，不经过它。

### 10.8 最小可行定义

传导链的 MVP 薄到出乎意料：

- **节点** = { 目标, owner, 状态, 产物, 门控 }
- **事件** = spawn / done / fail / escalate（外加 timeout 兜底）
- **不变量** = 每次 spawn 恰好一次回传；完成必经门控；活跃节点必有心跳

它跑起来不是因为规则聪明，而是因为规则笨而执着。

## 11. 上下文纪律：什么该注入，什么不该

上下文是 Agent 的"工作记忆"，也是最贵的资源（决定了成本与质量）。
**注入过多 = 噪音；注入过少 = 盲区。** 这里给出取舍准则。

### 该注入（常驻，开工前就有）

- 全局顶层原则、红线、宪法（第 4 节）
- 本岗位的职责 / 边界 / 上级 / 越界联系人（第 6 节）
- 本岗位的专属方法论 skills（低频、权威）

### 不该常驻（按需查，别占上下文）

- 高频变动的数据（正文、明细、日志、动态状态）—— 该"查"而不该"带"
- 与本职无关的其他单元细节
- 可搜索到的、量大的一次性内容

### 核心原则

> **常驻的是"身份 + 约束 + 方法论"（低频权威信息）；高频可变数据永远按需拉取。**
> 把高频可变的东西放进常驻上下文，是上下文爆炸和"局部正确整体崩盘"的共同元凶之一。

## 12. 权限与沙盒：边界管写，不管读

**边界存在的原因，从来不是阻碍信息获取，而是约束改动。**

一个最常见的做反：防御式地把**读写一起锁**。这会让 Agent 连想要的信息都拿不到
（只好"一直打电话"问人），而且被锁在连本职都干不了的范围里。

### 读放开，写收紧

**最准确的权限模型是"读写分离"：**

- **读 = 全放开。** 每个 Agent 都能看到整个工作库、获取所需信息**而不受限**。
- **写 = 按域/权限收紧。** 边界真正要管的是**改动**——不该它动的东西别动。

> **信息全通，改动受限。** 读放开让 Agent 不必因缺信息而一次一次通讯；
> 写收紧让它的破坏半径有限。**限制信息获取，就是一种"只把门关上但不出路"的设计**（见第 15 节反模式 B）。

### 边界的动机

- **做反（防御式）**："我限制它是怕它乱来。" → 结果它连信息都拿不到、还被锁死，
  停工 / 乱搞 / 汇报。
- **做对（导向式）**："边界让它专注本职，并在越界时有明确的出路。" → 它什么都看得到，
  清楚自己能动什么，也清楚动不了该找谁。

### 域内放开，跨域收紧

粗粒度分域（见 8）下，权限应随"域半径"走：

- **域内放开**：负责人在自己的工作域内放得开手脚，不被琐碎锁死。
- **跨域收紧**：只在要碰边界外目标时才需要上级 / 倒查路由（见 9）。

放开的是**域内的自由度**，不是**域边界本身的模糊**。

**边界要有"出口"，否则边界就是陷阱。** 设计权限时，和通讯契约（6.6）一起设计：

- 能动的：明确列给。
- 不能动的：不只要"禁止"，更要"禁止时该怎么走"（倒查负责人通知，见 9）。

**沙盒范围**是权限的物理层，约束 **写** 的实际执行半径（命令、文件写入、网络）。
它应跟"它该专注的那一亩三分地"一致——既不要大到能碰全局，也不要小到干不了本职。
读通常不受沙盒限制。

> **好的边界 = 读放开获取信息 + 写按域收紧 + 越界有清晰出路；差的边界 = 只锁不指路、连信息都限。**

## 13. 委派：负责人 Agent 为什么必须能动手

一个常见的错误设计：负责人岗位只做"规划 / 转发"，把活交给别人，自己不真的动手。
这有**上下文整洁**的好处（规划不占用执行上下文），但会把统筹心智全部压在用户头上——见第 14 节。

补充：**用一个"纯规划型"负责人 会让所有实际工作的上下文，碎片化到它下面的专职 Agent 里，
而它自己无力接住下属的失败、无力做"在边界内但没人管的"那些琐碎活。**

因此，负责人岗位 Agent 应具备两个能力，这通常意味着**它能委派下层的子岗位来实际干活**：

1. **委派（spawn）**：把大块的执行工作拆给专职子岗位，保持自己上下文整洁（这是好习惯）。
2. **接住**：当子岗位"动不了 / 越界 / 失败"时，能接手或再调度，而不是抛回给用户。
   接手的具体机制是传导链上的移交（见第 10 节）：传状态指针、不传记忆——接手者读库重建。

> 委派的正确动机是**上下文整洁**（不把执行细节塞进自己的长对话），
> 而不是"我懒得动手"。负责人能动手、也敢接烂摊子，才扛得住一摊。

## 14. 谁负责什么：责任层的划分

把"谁对什么负责"钉死，是防止集群失序的最后一道闸。这里有一个**清醒的责任分配**，
它承认 LLM 的认知现实，而不是追求全自主。

### 分层责任

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| **用户（人）** | 维护唯一真相源（全局规则/总则）；掌握最终拍板权；做 LLM 做不了的价值判断 | 逐条盯每个 Agent 的执行细节 |
| **负责人岗位 Agent** | 协调自己的域：派活、盯进度、接住子岗位的越界；跨边界时**倒查寻址**到对应负责人 | 替用户维护全局真相源；做最终项目裁决 |
| **专职子岗位 Agent** | 在本职边界内专注干活，产出高质量结果 | 越权处理边界外的全局决策 |

### 关于"动态全局规则"，诚实的结论

一个必须接受的事实：**LLM 不具备独立、自主、负责任地维护整个项目全局真相源的能力。**
它没有全局视野(注入只能给框架)，也没有自我纠偏的自愈力(需要人在环)。

因此：

> **全局真相源（静态 + 动态规则）的最终主人是用户。** 这不是逃避，而是**知人善任**——
> 在已知 LLM 缺陷后，把"决定全局走向"这一最需要判断力的职责，保留给能负责的人。
> **追求"由 Agent 全权自主引导的全自动化系统"，本身是一种不负责任的设计。**

但这绝不意味着用户要做"人肉交换机"。**用户的带宽用在一处：维护一份真相源 + 只在关键节点决策。**
日常的协调、派活、盯进度、处理越界，由负责人岗位 Agent 承担。
这样用户从"管几十个 Agent"降级为"管一份文档 + 几个负责人"——**心智负担才真正可承受。**

## 15. 失败模式与反模式

整理了这套架构会以哪些方式崩掉，以及对应的反制。**设计时对照自查。**

### 反模式 A：网状平级通讯
所有人随时能找所有人。→ 上下文被噪音污染；每个 Agent 被迫掌握全局组织图。
**改：可寻址点对点 + 分层 + 程序层注册表按需查询（第 8、9 节）。**

### 反模式 B：只锁不指路（含限制读）
权限把 Agent 锁住、甚至限制它读信息，却不给它越界出路。→ 它乱搞 / 停工 / 预期外破坏；
为拿信息疯狂"打电话"。**改：读放开、写按域收紧、越界可倒查寻址（第 9、12 节）。**

### 反模式 C：把统筹全抛给用户
用户当人肉交换机，逐个派活、逐个盯。→ 用户带宽崩溃，项目在用户处卡死。
**改：引入域 / 负责人岗位 Agent 承担协调，用户只维护真相源 + 关键拍板。**

### 反模式 D：切分靠直觉（或切得过细）
岗位 / 工作域边界拍脑袋，或细到极致。→ 边界与真实结构错位、频繁越界、集群震荡、
统筹黑洞。**改：先看领域中的关系结构，再粗粒度定域（第 7、8 节）。**

### 反模式 E：上下文灌满
把所有信息塞进每个 Agent 常驻。→ 噪音、成本爆炸、专注失败。
**改：常驻低频权威信息，高频可变量按需查（第 11 节）。**

### 反模式 F：全自主任务"扁平 + 无中层"
把一个大项目直接平铺成几十个无层级 Agent，没有负责人层。→
无人在环、无人能接住越界，一乱俱乱。
**改：粗粒度分域 + 每域有负责人兜底（第 8、13 节）。**

### 反模式 G：任务状态寄居在 Agent 上下文里
任务进度、产物位置、依赖关系只存在负责人的"脑子"里。→ 负责人一重启、一换岗，
全部进度归零；接手者两眼一抹黑。
**改：任务状态由程序层传导链单写者维护，与 Agent 生命周期解耦（第 10 节）。**

### 反模式 H：自报即完成
Agent 说"done"任务就流转为完成，没有独立验收。→ 谎报完成、带病交付，
波及下游的破坏被层层放大。
**改：门控是完成定义的一部分——状态流转到"完成"必经门控（第 10 节）。**

## 16. 启动清单：最小可运行的第一步

不要试图一次设计整个集群。从**一个最小的可运行切片**开始，验证后铺开。

1. **选一个边界清晰的小任务**（不是整个领域），例如"只处理某个子单元的一件具体产出"。
2. **画依赖**：这个子单元依赖了谁、被谁依赖？画出最小边界（见 7）。
3. **定义两个岗位**：一个"负责人"（统筹这一小块），一个或几个"专职子岗位"（干具体活）。
4. **写完整封装**：给每个岗位补全第 6 节的七个方面（上下文/skills/权限/沙盒/能力/通讯/委派）。
5. **注入全局约束**：把这一小块涉及的顶层原则 + 红线写进权威文档，自动注入。
6. **设计越界出口**：先写好——"子岗位动不了时找谁"、"负责人接不住找谁"。
7. **搭最小任务传导链**：按第 10.8 节的 MVP 定义（节点 / 事件 / 不变量）让每次
   spawn 都有回音、完成必经门控。
8. **跑一遍**：让负责人委派、子岗位干活、触发一次真实的越界，看它是否按设计走，
   而不是乱来。
9. **复盘边界**：把"这次频繁越界的地方"记下来——那是你的边界切错了，回头改。

> 一个切片的成功标准：**用户只做"维护真相源 + 关键拍板"，不用逐条盯执行；**
> Agent 在职责内自洽，越界时按设计的出口走而非乱搞。

## 17. 这份方法的上限与诚实声明

这套方法论建立在几个**有意为之的取舍**上，读它的人应该清楚它们的代价：

**它不为"全自主 Agent 系统"背书。** 它的责任分配明确保留了"人在环、人掌握全局真相源"，
因为这是对 LLM 认知现实最负责任的做法。如果你追求的是一个无需人监督、全权自治的集群，
这套方法不是你要的——但那种系统在当前是**不负责任的幻想**，不是成熟工作系统。

**它的瓶颈在设计者本身。** 这套方法把集群的上限押在了设计者身上：

- 对领域**结构的拆分能力**
- 对"多人/多岗多责"的团队管理水平

如果设计者拆分能力差，集群会比人类团队**更乱**——因为有消息损失的异步群，比吵架的人类更难协调。
**所以在动手前，先评估：我对这个领域够了解吗？拆分边界我有把握吗？**
没有把握，就当第 7 节没满足，先把领域中的关系结构摸清，不要硬切。

**它假设"可寻址点对点 + 分层"够用。** 如果某个领域确实需要高密度的交叉协调，
可寻址点对点可能会成为瓶颈——但那是少数，而且你应该先怀疑自己的边界拆分，而不是去加通讯。

## 18. 领域映射：它在软件工程里长什么样

**这一节供软件工程师对照落地。** 方法本身通用；这里告诉你通用概念 = 软件工程里的哪个具体家伙。

| 方法层概念 | 软件工程里的具体化 |
|---|---|
| 领域资产 / 工作库 | → 代码库（repository） |
| 单元 / 工作域 | → 模块 / 服务 / 包 / 目录 |
| 单元之间的关系结构 | → 依赖图、模块耦合、分层架构 |
| "某个产物被多方依赖" | → 公开接口 / 公共 API / 被多方 import 的模块 |
| 改动波及别处 | → 破坏性变更、破坏信号、连锁回归 |
| 跨单元共同口径 | → 跨模块契约、共享类型、约定 |
| 全局权威文档（注入） | → `AGENTS.md`、`CONTEXT.md`、架构总则 |
| 程序层注册表（通讯录） | → 一个维护"模块/服务 ↔ 负责 agent"映射的注册服务 |
| 任务传导链（动态状态的家） | → 任务状态机 + 事件流（spawn / done / fail 的事件溯源） |
| 节点运行轨迹 | → 审计日志 / 执行轨迹（谁在何时交付了什么，可回放） |
| 读放开写收紧 | → 能读全库、只在被授权的路径/模块内写 |
| 负责人 Agent | → 模块/领域 owner（如"前端负责人 agent"） |
| 委派（spawn） | → 派生子 agent 执行具体子任务，父保持上下文整洁 |

**一句话落地**：软件工程是这套方法论**最早也最成熟的一个实例**——它有现成的依赖图、
成熟的模块边界、成熟的"文件→归属"映射。但**同样的骨架**，可以搬到法规文献、
科研管线、供应链、法务合规等任何有"明确产出单元 + 依赖关系"的领域。

---

### 结束语

多 Agent 集群不是"把一群模型扔进一个仓库让它自己商量"。
它是一个**有分工、有边界、有层级、有责任、有纪律**的团队——无论它处理的是代码、文献、
配方，还是别的什么。

本章方法的核心就四句话：

1. **以"岗位"为单位设计，每个岗位是一份完整的能力与约束封装。**
2. **全局视野靠注入，协同靠上下文 + 可寻址的点对点路由，不靠网状消息。**
3. **人维护真相源、负责人 Agent 协调一摊、专职 Agent 专注本职——责任分层，心智负担才降得下来。**
4. **任务状态住在程序层：链从委派事件里长出来，门控决定完成，Agent 只是链上的节点。**

其中三大落点：**路由靠程序层注册表倒查（不是写死相邻），权限是读放开、写按域收紧（不是只锁不指路），任务状态由传导链单写者维护（不是寄居在 Agent 的上下文里）。**

按这份清单去切你的第一个最小切片，跑通它，再铺开。骨架通用，实例随领域而变。
